## 4. 已用实测确认的事实

1. **QEMU + HFS+ 根盘能进用户态**（今天的核心成果）：
   日志环出现 `bsd_init: done` → `SONGYUAN init: /sbin/launchd -> errno 0`，
   读到的 PC = `0x0000000100003fb4`（用户态地址）。
2. **真机无 fbcon + 真 UFS 根卷引导不 panic**（120 秒内 adb 不回、无自动复位）；但“是否挂上 UFS 根卷、是否 exec”**没有证据**（无显示、无日志通道）。
3. **fbcon 是坏的**：`pc=_fbcon_init+0xb4` 写 `0xfffffff1_6bb00000`（IO VA）→ 数据中止 →
   `vm_fault_internal(map=NULL)` → 读 `[0+0x9e]` 递归 → 异常栈压穿。
   把 fbcon 高度从 2668 降到 1440（6.9 MB）**并没有解决**（QEMU 仍到 `_vm_fault_internal.cold.2`）。
   → 结论：4 KiB 布局下 fbcon 早期映射不成立，**已放弃 fbcon**（`SONGYUAN_NO_FBCON=1` 成为默认）。
4. **USB gadget 从未执行**：构建定义 `FUXI`，而 `sweet_usb_probe()` 只在 `#else`（非 FUXI）分支调用（`bsd/dev/sweet_ufs.c`）。因此 Windows 上永远看不到 COM/网卡。
5. 已尝试并**失败**的真机日志通道（不要重复）：
   - `0216` ramoops 落盘（panic 前写 `ramoops-region` 0xff400000，console 1 MiB，无 ECC，`persistent_ram_buffer` 头）——没等到复位，未验证
   - `0217/0218` 软件看门狗（线程睡 90 s 后 panic）——不触发
   - `0219/0220` 硬件 WDT（`qcom,msm-watchdog`@0x17600000，RST 0x4 / EN 0x8 / BITE 0x14，喂 60 s 后停）——190 s 仍无复位
   - 这些补丁仍在 `xnu/patches/0216..0220`，如不需要可从 `series.songyuan` 移除
6. ~~`io_submap` 只有 8 MB，而 ADT 声明帧缓冲 11 MiB~~ —— **11 MiB 这个数字是错的**：
   真机 DT 的 `splash_region` 是 `<0x0 0xfc800000 0x0 0x2b00000>`（43 MiB），
   一帧 1200x2608x4 = 12.5 MiB 完全装得下。详见 `device/DISPLAY-2026-10-26.md` §2/§3。
7. **真机 FDT 已取回并解析**（2026-10-26 17:51，`/sys/firmware/fdt`，977,454 字节，
   工具 `tools/fdt_dump.py`）。据此修正了两个板级常量：
   - splash 大小 11 MiB → **43 MiB**（`0x2b00000`，与 pandora 相同）；
   - 面板高度 2668 → **2608**（活动面板 `qcom,mdss_dsi_songyuan_42_0d_0a_p2_dsc_cmd`，
     DT 的 panel-width/height、`/sys/class/drm/card0-DSI-1/modes`、`wm size` 三处一致）。
   旧的 2668 和 11 MiB 在真机任何一处都找不到出处。
8. **QEMU 屏幕回读此前是坏的，已修好并实测**：`qemu_boot.py` 固定从 `0x9c000000` 取图，
   而 loader 一直往 `0xfc800000` 画 —— 所以之前 `phonefb*.png`/`clcd.png` 的“全黑”
   是工具 bug，**不是**“AppleCLCD 不出图”的证据。修复后 QEMU 能直接读出
   1200x2608 的 loader 画面（无斜切，顺带验证了 stride 4800）。从此内核侧任何刷屏都可在
   QEMU 的 PNG 里看见（`.scratch/qemu/fbcheck.png`）。
9. **ADT 对比结论（显示假设已排除）**：用同一 seed 生成 pandora 与 songyuan 两份 ADT
   逐字段比对，`/arm-io/disp0` 及全部显示相关属性**完全相同**；只有身份字符串和
   `/sweet-fbcon` 的板级几何不同。→ “把 pandora 的显示属性补进 ADT”这条路已经走完，
   **没有东西可补**，不要再查 ADT。

## 5. 下一步（按顺序，含验证方式）

1. **显示：先定性，别再改代码**。`-NoFbcon` 引导后拍一张照，只看屏上是哪一种：
   - 还留着 loader 的控制台（`PANDORA loader v1 ...`）→ 内核没接管/没到用户态，
     问题在启动链而不是显示驱动；
   - 纯黑 → 面板/背光被关（查 `0079`/`0136`/`0137` 的亮度路径）；
   - 花屏/斜切 → 几何问题，本次已修正（1200x2608），先重试。
   背景与证据：`device/DISPLAY-2026-10-26.md`（§1 ADT 对比、§2 真机 DT、§5 链路结构）。
2. **真机日志通道 = 唯一卡点**：`sweet_usb_probe()` 被 `bsd/dev/sweet_ufs.c` 的
   `#if defined(FUXI) … #else … #endif` 编译掉了（songyuan 同时定义 `FUXI` 和 `PANDORA`），
   `0215` 只换了 USB 描述符、没改调用点 —— 这就是“USB 控制台从未出现”的原因。
   一行补丁把调用挪到分支外即可（**只挪 `sweet_usb_probe()`，不要连带 `sweet_log_start()`**，
   后者会写 ufsroot0 尾部、破坏 APFS 镜像）。同时按 DT 核对 QUSB2 PHY 基址
   （DT 是 `hsphy@88e3000`，补丁里写的是 SM8550 的 `0x088e2000`）。
   备选：`0129` 的 UFS 日志文件（已实现、pandora 验证过），但需要 `ufsrw=1`，
   与硬规则冲突，**必须先明确同意**。
3. **触摸**：pandora 的 TouchComm 补丁（`0130/0131/0133/0134/0135/0142`）可复用（显示之后再说）。
4. **Wi-Fi**：`0099-fuxi-wlan.patch` 是参考；songyuan 是 WCN786x（DT 里 `wcn786x`）。
5. **GPU**：`0162`–`0198` pandora GPU 序列；缺的三个 pandora 尾补丁（`0212-fbdump-swap`、`0216-gic-gpu-interrupt`、`0219-gpu-windows`）编号与我们冲突，需要时改名加入。

## 6. 设备信息与安全

- 序列号 `a928b15f`，型号 M098FE，codename `songyuan`，SM8850，槽 `_b`，已解锁（`ro.boot.flash.locked=0`），KernelSU 可 `su`
- 真根卷：`/data/local/tmp/iosroot.img`（2.7 GB APFS，首扇区 `NXSB`）；extent 工具 `/data/local/tmp/extents`
- **硬规则**：
  1. 只 `fastboot boot`，**绝不** flash/erase/`--set-active`
  2. **绝不**传 `ufsrw=1`（昨天写坏过 userdata）
  3. 每次引导前重读 extents 并与上次比对，不一致就中止
  4. boot.img 先过 `mkbootimg_v4.py` 头校验
- 手机 panic 后若没有自动复位，只能长按电源 10 秒（硬件 WDT 方案未生效）

## 7. 坑与注意

- 本地用 `git apply` 重放补丁时，补丁文件必须是 **LF**（用 `git show HEAD:...` 取 blob 再写，避免 PowerShell 写成 CRLF）
- CI 里 blacktop 的 `build.sh` 会**全量应用** `dxb/patches/`，所以 `xnu.yml` 按 `series.songyuan` 清单逐个复制
- `debug=0xc` 不会自动复位（`DB_REBOOT_ALWAYS=0x100000` 才复位）
- git 走本地代理 `127.0.0.1:7897`（已全局配置）
- 大文件都放 E 盘；npm/pip 缓存已改到 `E:\songyuan\cache`

## 8. 今天的教训（写在最前面提醒自己）

- 不要在没有验证通道的情况下连续改补丁；先建立“能看见结果”的最小闭环
