# 显示专项：真机 DT 实测、ADT 对比与两个板级常量错误（2026-10-26 晚）

本文记录三件有实测支撑的事，目的是结束“猜补丁、改一版、失败”的循环：

1. pandora 与 songyuan 的 ADT 显示节点**逐字段相同**——上一轮“差异在 ADT 板级数据”的假设不成立；
2. 从**真机 FDT** 读出了显示相关的全部事实，并据此发现我们有两个板级常量是错的
   （splash 43 MiB 写成 11 MiB、面板高度 2608 写成 2668）；
3. **QEMU 屏幕回读此前一直是坏的**（dump 的地址不是 loader 真正写的那块），所以
   “QEMU 里 AppleCLCD 全黑”不是一个有效结论；修好后 QEMU 已经能看到真机几何下的
   loader 画面（`device/qemu-fbcheck-2026-10-26.png`，1200x2608 正确渲染）。

---

## 1. ADT 对比：显示节点完全相同（已实测）

方法：直接 import 两个生成器、用同一个 seed 调 `build()`，递归比对每个节点的每个属性
（脚本见本文末尾）。真机与 QEMU 两种配置都比了一遍。

| 节点/属性 | pandora | songyuan | 差异 |
|---|---|---|---|
| `/arm-io/disp0` 全部属性（device_type/compatible/canvas-width/canvas-height） | 同 | 同 | **无** |
| `/arm-io` 其余子节点（gic/wdt） | 同 | 同 | 无 |
| `/sweet-fbcon` reg/width/height/stride | 0xfc800000/0x2b00000/1220x2656/4880 | 0xfc800000/0x2b00000/1200x2608/4800 | 板级几何（见 §3） |
| `/chosen` display-scale | 3 | 3 | 无 |
| `/compatible`、firmware-version、unique-chip-id | pandora 标记 | songyuan 标记 | 仅身份 |

结论：

- **`disp0` 一个字节都不差**。pandora 能出图而我们不能，不可能是 ADT 少写了显示属性。
- `/arm-io/disp0` 只提供 `device_type=display-subsystem` 和 canvas 尺寸；物理屏几何和
  帧缓冲地址走的是 **PE_video**（loader 填的 boot_args），不是这个节点。
- 因此“把 pandora 的显示属性补进来”这条路已经走完，**没有东西可补**，不要再查 ADT。

## 3. 两个板级常量错误（本次修正）

| 常量 | 旧值 | 正确值 | 依据 | 影响 |
|---|---|---|---|---|
| splash 大小 | `0x0b00000`（11 MiB） | `0x2b00000`（43 MiB） | `splash_region` | ADT `sweet-fbcon.reg`、fbcon 映射长度、loader 清屏边界 |
| 面板高 | 2668 | **2608** | 面板 DT + DRM 模式 + `wm size` | loader 清屏/排版、`sweet-fbcon.height`、QEMU PNG 解码 |

已改：`tools/mkadt_songyuan.py`、`shim/loader/loader.c`、`tools/qemu_boot.py`、
`wsl/songyuan_board.h`。旧的 2668 和 11 MiB 在真机的任何一处 DT/DRM/sysfs 里都找不到出处，
来源不明（大概率是把 2608 读成了 2668）。

副作用（好的）：一帧 1200x2608x4 = 12.5 MiB，43 MiB 的 region 完全装得下，
所以“写到声明范围外 1.21 MiB、属未定义行为”这条旧的担忧**不成立**，可以删掉。

## 4. QEMU 屏幕回读此前的 bug（已修，已实测）

`tools/qemu_boot.py` 里 `dump_fb()` 固定从 `0x9c000000` 取图，而
`shim/loader/loader.c` 无论 QEMU 与否都往 `0xfc800000` 画。于是：

- 之前所有 `--phone-fb` 的 PNG（`phonefb*.png`、`clcd.png` 等，5122 字节）读的都是没人写过的
  QEMU 内存，**全黑是工具的问题，不是 AppleCLCD 的问题**；
- 因此“QEMU 无法验证显示”这个结论要撤销——至少 loader/内核往帧缓冲写的东西现在能看见。

修复后（`--seconds 8`，`-icount shift=3`）同一台 QEMU 直接读到：

```
device/qemu-fbcheck-2026-10-26.png   1200x2608   loader 控制台文字完整、无斜切
```

（命令：`$env:SONGYUAN_QEMU_WORK=<work>; python tools/qemu_boot.py --stem fbcheck --seconds 8`）

这同时验证了 1200x2608/stride 4800 是对的（斜切会立刻暴露 stride 错误），
并且给后面的显示工作一个“能看见结果”的闭环：**任何内核侧的刷屏都会出现在这张 PNG 里**。

## 5. 显示链路的真实结构（读 0046 得到的结论）

`SweetFramebuffer.cpp` 里的 `AppleCLCD` 是**纯软件帧缓冲**：

- `start()` 用 `PE_current_console(&video)` 拿到 loader 填的 `PE_video`（物理地址、宽高、stride）；
- 把这块物理内存包成 IOSurface；`present()` 把 iOS 的层拷贝进去；
- 它**不碰 MDP/DSI/DSC**，也从不主动扫屏；
- 面板是 DSC command mode（`dsi_cmd_mode`），ABL 交棒后 MDP 仍在从 splash_region 扫出。

所以“屏幕不出图”只可能有三类原因，且**与 ADT 无关**：

1. 内核没跑到用户态 → 没有任何人 present（真机当前无法排除，这是主要嫌疑）；
2. 跑到了但 present 的内容不对（几何/格式）→ 现在 QEMU 可验；
3. 面板/背光被关掉（patch 0079/0136/0137 的亮度路径）→ 需要真机确认屏上是“loader 画面冻结”还是“纯黑”。

第 3 点只要下次开机拍一张照就能定性，**这是成本最低的一个判据**。

## 6. 下一步（按验证成本排序，不再猜）

1. **拍照定性**：`-NoFbcon` 引导后屏上是不是还留着 loader 的控制台（`PANDORA loader v1 ...`）？
   - 留着 → 内核没接管/没到用户态，问题在启动链，不在显示驱动；
   - 纯黑 → 面板/背光被关，查 0079/0136/0137；
   - 花屏/斜切 → 几何/stride，现已修正，先重试。
2. **真机日志通道**：`sweet_usb_probe()` 被 `bsd/dev/sweet_ufs.c` 的
   `#if defined(FUXI) ... #else ... #endif` 编译掉了（songyuan 同时定义 `FUXI` 和 `PANDORA`），
   `0215` 只改了 USB 描述符、没有改调用点——这就是“USB 控制台从来没有出现过”的原因。
   一行补丁把调用挪到分支外即可（**只挪 `sweet_usb_probe()`，不要连带 `sweet_log_start()`**，
   后者会写 ufsroot0 尾部，破坏 APFS 镜像）。注意 §2.3 的 PHY 基址差异。
3. **UFS 日志文件**（`0129`，已实现，pandora 验证过）：需要 `ufsrw=1` 和 pinned
   `pandora-log-extents`。与硬规则“绝不 `ufsrw=1`”冲突，**需要明确同意**才做；
   写保护已经限定在日志文件自己的块（`pl_inside`），但这不是零风险。
4. 触摸：pandora 的 `0130/0131/0133/0134/0135/0142` 可复用（显示之后再说）。
