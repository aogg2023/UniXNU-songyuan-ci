## 一条命令跑一圈

```powershell
. .\tools\env.ps1                      # PATH + GH_TOKEN + SONGYUAN_WORK/DL/IPSW + 回到仓库根
gh workflow run xnu -R aogg2023/UniXNU-songyuan -f machine_config=SONGYUAN
gh run watch -R aogg2023/UniXNU-songyuan        # 约 4 分钟
gh run download <run-id> -R aogg2023/UniXNU-songyuan -n xnu-kernel-gz -D $env:SONGYUAN_WORK\kernel

.\tools\boot_songyuan.ps1 -DryRun      # 只出 boot.img，不碰手机
.\tools\boot_songyuan.ps1              # 读 extents → ADT → payload → loader → fastboot boot
```

`boot_songyuan.ps1` 每次启动前都会**重新读一次 extents**（旧事故的教训：文件被 f2fs 搬走，
extents 就指向别的块），并且只 `fastboot boot`，从不写分区。

## 今天在设备上核实的事实

1. **ADT 里的 UFS 基址是对的**：设备 DT `soc/ufshc@1d84000/reg` = `0x01d84000, 0x3000`
   （`reg-names = ufs_mem, ice, mcq_sqd, mcq_vs`，后三段是 ICE/MCQ，驱动不用）。
   → 11.30 里“UFS 基址可能不对”这条假设**排除**，二次 panic 另有原因。
2. 顺带核对了同批常量：`kgsl-smmu@3da0000` 长度 `0x40000`、`qcom,gmu@3d37000` 长度 `0x68000`、
   `kgsl-3d0@3d00000` 基址 `0x03d00000` —— 与 `mkadt_songyuan.py` 全部一致。
3. **`iosroot.img` 没丢**：`/data/local/tmp/iosroot.img`，2,701,766,656 字节，首扇区 0x20 处是 `NXSB`（APFS）。
   配套的 `/data/local/tmp/extents`（arm64 静态）也还在，可以直接重读 extent 表。
4. `extents` 的 pin 两种方法都返回 `Operation not supported`（KernelSU 下没有 f2fs 的 pin ioctl 权限/实现），
   所以文件的块**可能被 GC 搬走**：每次启动前重读、并和上一次的 JSON 比对。
   连续两次读取结果一致（`device/extents/iosroot-20261026-105938.json`，9 段、659611 块）。
5. 引导链状态：`ro.boot.flash.locked=0`、`verifiedbootstate=orange`（已解锁），当前槽 `_b`，userdata 余量 212 GB。
